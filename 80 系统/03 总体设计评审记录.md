# 个人知识库总体设计评审记录

> 本文记录对 [[80 系统/01 知识库设计说明|个人知识库总体设计方案 v3.1]] 和 [[80 系统/02 实施路线图|实施路线图]] 的 Gate A 评审。结论为“有条件通过”：总体方向正确，但在隐私边界、命名、领域归属、验证模型和证据规则冻结前，不进入 Phase 2。

# 1. 总体结论

当前方案已经具备长期个人知识库所需的主要骨架：

- 顶层按信息角色划分，而不是把项目、书籍、数学和日记混在同一维度；
- 数学与图形学平级，基础理论可以被 AI、机器人和音视频复用；
- 来源、正式知识、项目、实验和输出形成可追溯闭环；
- 文件夹、Properties、MOC、Manifest 和 Git 的职责基本清晰；
- 采用小规模试点和阶段门禁，避免一次性全量重构。

当前不建议推翻方案，但 Gate A 不能直接判定为通过。以下问题需要先形成明确决策。

---

# 2. 阻断项

## F-01：公开仓库与私人信息边界尚未定义

### 风险

当前 GitHub 仓库是公开仓库，而总体设计包含：

- 收件箱；
- 项目过程和工作记录；
- 健康、财务和生活责任领域；
- 日记与回顾；
- 未发布输出；
- 可能包含雇佣、设备、账户和个人决策信息的来源或附件。

如果按当前目录直接使用，很容易把私人、医疗、财务、工作或身份信息提交到公开仓库。该风险高于目录和元数据问题，必须在继续建设前解决。

### 可选方案

#### 方案 A：单一私有 Vault

把当前仓库改为私有，所有个人行动、知识和日记保存在同一个 Vault。未来通过导出或独立发布流程公开部分知识和输出。

优点：结构最简单、跨目录链接最稳定、维护成本最低。

#### 方案 B：私有 Personal OS + 公开 Knowledge Core

- 私有库：收件箱、项目、责任领域、日记、私人来源和未发布输出；
- 公开库：正式技术知识、可公开来源笔记、实验、公开输出和系统规范。

可将公开 Knowledge Core 作为私有 Obsidian Vault 中的普通子目录或 Git submodule，使 Obsidian 可以统一索引。

优点：公开分享与私人管理边界最清晰；缺点是跨仓库链接、同步和发布流程更复杂。

#### 方案 C：保持当前仓库公开，但只建设公开知识库

移除或禁止使用收件箱、私人项目、健康财务领域和日记等个人操作目录。该方案不再是一套完整个人知识操作系统，而是公开知识库。

### 建议

默认推荐方案 A；只有明确需要长期公开知识正文时才选择方案 B。不推荐在公开仓库中依靠“自己记得不要提交敏感内容”作为安全策略。

### 状态

`decision-required`

## F-02：责任领域命名已确认

### 决策

顶层目录已从：

```text
20 领域
```

调整为：

```text
20 责任领域
```

统一术语：

- Area = 责任领域；
- Domain = 知识领域；
- Module = 知识模块；
- Topic = 知识主题。

该调整解决了 PARA 长期责任与数学、图形学、AI 等知识领域之间的中文语义冲突。

### 状态

`accepted`

关联决策：[[80 系统/60 ADR/ADR-0005-责任领域命名|ADR-0005：责任领域命名]]。

## F-03：验证状态不应是单选线性枚举

### 问题

当前属性示例：

```yaml
verification: experiment-reproduced
```

但一篇文章可以同时具备：

- 核对官方或权威来源；
- 完成数学推导；
- 通过最小实验；
- 在生产环境中使用。

这些证据类型不是严格互斥，也不是单一线性等级。使用单值会丢失证据维度，或者迫使维护者只记录“最高状态”。

### 建议模型

改为列表：

```yaml
verification:
  - source-checked
  - derived
  - experiment-reproduced
```

并在正文中通过链接记录具体证据：

```markdown
## 验证证据

- 推导：本文第 4 节
- 实验：[[投影矩阵与 NDC 映射实验]]
- 规范：[[Vulkan Specification]]
```

`maturity` 和 `lifecycle` 继续使用单值。

### 影响

需要同步调整：

- Frontmatter 规范；
- 模板；
- 校验脚本；
- 现有试点文章；
- Manifest 中的验证字段。

### 状态

`recommended-change`

## F-04：来源权威不能使用单一全局排序

### 问题

当前来源规则使用统一顺序：推导与实验、官方文档、论文、教材、文章、代码和经验。

不同问题的权威来源不同：

- API 的规范性行为以标准和官方文档为主；
- 数学结论以证明、推导和教材为主；
- 研究方法以原始论文和复现实验为主；
- 某一版本引擎的真实行为可能以源码、测试和 Frame Capture 为主；
- 性能结论必须以明确环境下的测量为主。

将源码或实验固定排在教材之后，可能导致对实现行为的错误判断；将实验固定排在规范之前，也可能把驱动缺陷误写成 API 语义。

### 建议模型

采用按声明类型选择证据：

| 声明类型 | 首选证据 |
|---|---|
| 数学定义与定理 | 推导、证明、权威教材 |
| API 与标准语义 | 标准、规范、官方文档 |
| 科研方法与新算法 | 原始论文、作者资料、复现实验 |
| 具体实现行为 | 对应版本源码、最小实验、调试捕获 |
| 性能结论 | 固定环境的基准、Counter、对照实验 |
| 工程经验 | 生产记录、复现条件、适用边界 |

证据之间冲突时，不强行合并，应记录“规范语义”和“观察行为”的差异。

### 状态

`recommended-change`

# 3. 重要优化项

## F-05：知识领域边界需要形成正式判定表

以下领域最容易产生重复：

| 知识领域 | 主职责 |
|---|---|
| 03 计算机科学 | 数据结构、算法、计算机组成、操作系统原理、网络原理、编译原理、并行计算理论 |
| 04 图形学与渲染 | 几何、成像、渲染算法、GPU 渲染管线、渲染器通用架构 |
| 05 人工智能与数据科学 | ML/DL 模型、训练、推理、生成模型、LLM、RAG、Agent 和 AI 工程 |
| 06 软件工程 | 编程语言实践、代码设计、架构方法、测试、构建、依赖、协作和质量工程 |
| 07 系统与平台 | Windows/Linux/macOS/WSL、驱动、工具链、部署和平台特定排障 |
| 08 游戏引擎与实时应用 | UE、Unity、Qt/QML、Three.js 等具体引擎或框架的对象模型、源码和实践 |
| 09 音视频与多媒体 | 编解码、容器、同步、播放器、WebRTC 和媒体管线 |
| 10 嵌入式、机器人与智能驾驶 | SoC、ROS、传感器、定位、地图、SLAM、感知、规划和领域集成 |

通用理论放基础领域，平台和业务上下文建立应用文章。

示例：

```text
计算机科学/任务调度理论
软件工程/通用任务系统设计
图形学/渲染任务调度
UE5/TaskGraph 与 RDG
```

建议把该表加入总体设计正文，并为跨领域文章增加主归属判定流程。

## F-06：MOC、学习路线和索引需要进一步区分

当前都使用 `type: map`，职责可能重叠。

建议增加：

```yaml
map_kind: moc
```

允许值：

- `moc`：表达主题网络和当前内容；
- `learning-route`：面向目标的有序学习路径；
- `index`：尽量完整的查找入口；
- `dashboard`：面向行动和状态的视图。

同一个主题可以有 MOC 和学习路线，但两者不得复制整段说明。

---

## F-07：最小 Frontmatter 仍需降低手工维护成本

建议正式知识的核心必填项为：

```yaml
id:
type:
domain:
maturity:
lifecycle:
```

以下属性按条件要求：

- `verification`：有验证证据时填写列表；
- `sources`：进入 `draft` 或更高成熟度时至少一个，原创推导或经验可链接实验/项目证据；
- `versions`、`platforms`：版本敏感文章必填；
- `legacy_id`：迁移文章填写。

`created` 和 `updated` 应由模板、脚本或 Git 获取，不应成为高频手动维护负担。

---

## F-08：公开仓库需要来源文件、附件和版权策略

无论选择单库还是双库，都应明确：

- 不把受版权保护的整本书籍提交到公开仓库；
- 来源笔记保存书目信息、章节定位和个人重述；
- 引用只使用必要的短摘录，并记录页码；
- `_assets` 只保存有权公开的图片、自己生成的图和许可明确的素材；
- 私人截图、合同、医疗报告和账户材料不得进入公开仓库；
- 大文件需要明确 Git LFS、外部存储或不入库策略。

---

## F-09：顶层编号 `70` 的空缺需要说明

当前从 `60` 跳到 `80`。该设计本身没有问题，但应明确：

- `70` 是刻意保留的扩展槽；或
- 不承诺编号连续，`80 系统` 和 `90 档案` 是语义固定编号。

避免未来为了“填满编号”随意增加顶层目录。

# 4. 已通过项

以下设计可以在 Gate A 中直接保留：

1. 顶层按信息角色组织；
2. 数学与图形学平级；
3. 来源与正式知识分离；
4. 项目管理过程、输出保存成果；
5. 文件夹表达稳定归属、Properties 表达动态状态；
6. 不建立独立卡片顶层目录；
7. 一个基础概念维护一个完整主解释，允许应用文章；
8. 实验文章与可执行代码分离；
9. 未建设主题延迟实例化；
10. A/B/C 属于学习路线或 Manifest；
11. 迁移采用小批次并保留 `legacy_id`；
12. 使用 MOC、Manifest、ADR、CI 和 Git 形成治理闭环；
13. Phase 0～8 的总体推进顺序；
14. 当前两本书作为试点来源，而不是目录模板。

# 5. PR 和阶段建议

当前 PR 同时包含架构基线和第一批试点内容，严格来说混合了设计与内容。

由于仓库此前几乎为空，试点内容用于证明设计能够运行，因此可以将它视为一次性的 Bootstrap 例外，不必为了形式纯度重做提交历史。

建议：

1. 先解决 F-01～F-04；
2. 完成 Gate A 评审；
3. 在当前 PR 中完成 Phase 1 试点复盘，而不是继续增加 Phase 2 正文；
4. 将当前 PR 作为 `v0.2.0-design-baseline` 合并；
5. 后续光栅化、PBR、API 和迁移分别使用独立内容 PR。
