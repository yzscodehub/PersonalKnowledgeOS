# D2 知识对象与导航模型

## 1. 目标

D2 负责冻结“正式知识由哪些对象组成，以及这些对象如何被命名、关联、导航、演进和替代”。

D2 解决：

```text
一篇笔记应该是什么类型
一个主题应该拆成几篇文章
多个重复版本如何选择主解释
标题、路径和 ID 如何长期稳定
目录、Properties、标签和链接分别做什么
MOC、学习路线、索引、仪表盘和 Manifest 如何协作
跨领域主题如何组织
过时知识如何替代并保护历史链接
```

D2 不负责书籍阅读、项目回流和发布等完整流程；这些属于 D3。也不提前建设各知识领域的大量正文；领域蓝图属于 D4。

---

# 2. 知识对象分层

知识库中的知识对象分为四层。

## 2.1 正式知识文章

正式知识文章保存可长期复用的解释、推导、算法、系统、实现和验证结果。

允许的正式类型：

```text
concept
 theory
algorithm
system
implementation
api-reference
experiment
troubleshooting
comparison
```

实际 Frontmatter 不包含上面代码块中 `theory` 前的额外空格。

`principle` 不再作为独立正式类型。所谓“原则”根据内容分别归入：

- 概念边界或经验规律 → `concept`；
- 有明确假设、推导或理论依据 → `theory`；
- 系统治理原则 → `system-design` 或治理规则。

## 2.2 地图与导航对象

```text
map + map_kind: moc
map + map_kind: learning-route
map + map_kind: index
map + map_kind: dashboard
```

它们组织、排序、查找或展示知识，但不替代正式文章。

## 2.3 规划对象

Manifest 保存尚未实例化或正在建设的知识主题：

- 稳定主题 ID；
- 主归属；
- 目标文章类型；
- 建设状态；
- 依赖和路径；
- 当前路线中的优先级；
- 来源和验证要求。

Manifest 是建设计划，不是所有 Markdown 文件的人工总目录。

## 2.4 证据和行动对象

来源、项目、输出和日记不属于正式知识文章，但会生产、验证和使用知识。它们的主归属由 D1 决定，通过正文链接与知识对象连接。

# 3. 九种正式知识文章

## 3.1 `concept`：概念文章

回答：

> 它是什么？不是什么？由哪些关键属性定义？与相邻概念的边界在哪里？

适合：

- 点与向量；
- Clip Space；
- Descriptor；
- 时间基；
- 向量空间中的基。

推荐结构：

```text
问题与范围
定义与约定
核心模型
边界与相邻概念
典型应用
误区
验证证据
知识关系
来源
```

不要写成术语字典。达到 `draft` 后，应包含能够区分相邻概念的边界和至少一个应用或反例。

## 3.2 `theory`：理论文章

回答：

> 在哪些假设下，为什么结论成立？如何推导、证明或建立形式模型？

适合：

- 透视投影矩阵推导；
- BRDF 的数学性质；
- 傅里叶变换基础；
- 概率分布和估计理论。

推荐结构：

```text
问题与范围
符号、定义和假设
命题或核心结论
推导／证明
直觉解释
边界和反例
数值或实验检查
应用
来源
```

`derived` 只能在正文存在可定位推导、证明或机制推演时使用。

## 3.3 `algorithm`：算法文章

回答：

> 输入是什么？输出是什么？步骤和不变量是什么？复杂度和失败条件是什么？

适合：

- BVH 构建；
- 齐次裁剪；
- 重心坐标光栅化；
- A*；
- 音视频同步调度算法。

推荐结构：

```text
问题与适用范围
输入、输出和前置条件
核心思想
步骤或伪代码
正确性／不变量
复杂度
数值与工程问题
变体和选择
验证
来源
```

只罗列代码调用不是算法文章；具体 API 对象流程应进入 `api-reference` 或 `implementation`。

## 3.4 `system`：系统文章

回答：

> 系统由什么组成？数据、状态和所有权如何流动？生命周期和失败路径是什么？

适合：

- RenderGraph；
- 材质系统；
- Shader 变体系统；
- 音视频同步系统；
- RAG 系统架构。

推荐结构：

```text
问题和系统边界
需求与非目标
组件和职责
数据流与控制流
状态机和生命周期
接口与不变量
失败路径和恢复
并发、同步和资源所有权
性能和可观测性
实现映射
验证证据
```

系统文章描述通用架构。某个引擎或项目中的具体实现放在 `implementation` 或应用文章中。

## 3.5 `implementation`：实现文章

回答：

> 一个通用概念在明确环境中如何实现，关键数据结构、资源生命周期和权衡是什么？

适合：

- Metal 中的 CVMetalTextureCache 管理；
- DX12 中的 Descriptor 分配器；
- 自研引擎的材质 Pass 实现；
- 软件光栅器实现。

推荐结构：

```text
实现目标和环境
依赖的基础知识
总体结构
关键数据结构
执行流程
资源和生命周期
线程与同步
错误处理
性能与质量
测试和调试
限制和后续演进
```

实现文章必须声明平台、版本或代码上下文；通用理论链接主文章，不重复完整基础解释。

## 3.6 `api-reference`：API 文章

回答：

> 接口的规范语义、对象生命周期、调用约束、状态和版本差异是什么？

适合：

- Vulkan `vkCmdPipelineBarrier2`；
- DX12 Root Signature；
- Metal `MTLRenderPipelineState`；
- FFmpeg `avcodec_send_packet`／`receive_frame`。

推荐结构：

```text
功能与范围
规范和版本
对象、参数和返回值
生命周期
状态、同步和线程约束
最小调用流程
错误和边界
性能影响
跨平台对应
验证证据
官方来源
```

API 文章默认 `version_sensitive: true`。规范语义与某个驱动或引擎行为必须分开记录。

## 3.7 `experiment`：实验文章

回答：

> 要验证什么？在什么环境和控制条件下，得到了什么可复现结果？

适合：

- Reversed-Z 精度对比；
- Shader 变体编译时间测试；
- 视频同步策略对比；
- 不同纹理格式性能测试。

推荐结构：

```text
问题和假设
环境
输入、变量和控制条件
步骤和断言
原始结果
分析和结论
局限和威胁
复现方式
验证的知识与来源
```

`experiment-reproduced` 只有在代码、数据、步骤或其他复现方式可用且结果已经重新运行时添加。

## 3.8 `troubleshooting`：故障文章

回答：

> 在什么环境出现什么症状？如何排除假设、确认根因、修复并验证？

适合：

- Seek 后音视频不同步；
- WMI Provider Host 高占用；
- Vulkan Validation 错误；
- 非均匀缩放导致法线错误。

推荐结构：

```text
症状和影响
环境和版本
复现条件
预期与实际结果
假设和排查过程
根因
修复方案
修复验证
预防和监控
相关知识与来源
```

只记录“试了某方法就好了”不能达到 `stable`；必须说明根因或明确仍是经验性修复。

## 3.9 `comparison`：对比文章

回答：

> 在哪些评价标准和上下文下，多个方案有什么差异，应如何选择？

适合：

- Forward 与 Deferred Rendering；
- DX12、Vulkan 与 Metal 的资源绑定；
- UASTC 与 ETC1S；
- BVH 与 KD-Tree。

推荐结构：

```text
决策问题和适用上下文
候选方案
评价标准
可比条件和版本
逐项对比
共同点和不可比项
决策矩阵
场景化建议
验证证据
来源
```

不使用没有上下文的“最好”“更先进”结论。平台、版本和工作负载不同的测量不得直接混合。

# 4. 文章类型选择

按问题选择类型，而不是按资料形式或文件长度选择。

```text
主要回答“是什么”              → concept
主要回答“为什么成立”          → theory
主要回答“如何计算”            → algorithm
主要回答“系统如何协作”        → system
主要回答“在某环境如何实现”    → implementation
主要回答“接口契约是什么”      → api-reference
主要回答“如何验证”            → experiment
主要回答“如何定位并修复故障”  → troubleshooting
主要回答“如何选择”            → comparison
```

一篇文章只能有一个主 `type`。文章可以包含辅助章节，例如理论文章包含实现提示，但主问题决定类型。

出现两个同等重要的问题时，优先拆分为两篇文章并互相链接。

# 5. 文章拆分规则

## 5.1 应当拆分

满足以下任一条件时考虑拆分：

- 文章同时回答两个可以独立复用的核心问题；
- 两部分有不同的前置知识、验证方式或生命周期；
- 通用理论和具体平台实现混在一起；
- 稳定概念和版本敏感 API 混在一起；
- 故障案例中的根因已经形成通用机制文章；
- 一部分可以被多个领域应用，另一部分只属于单一上下文；
- 更新其中一部分经常迫使无关部分一起改版。

## 5.2 不因这些原因拆分

- 来源来自不同书籍；
- 同一文章出现在多条学习路线；
- 文章较长但仍只回答一个问题；
- 同一原理在不同项目中被使用；
- 只是希望让目录看起来更细；
- 不同 API 共享同一基础理论。

## 5.3 拆分步骤

1. 写出原文章的核心问题；
2. 为每个候选子文章写一句独立问题；
3. 确定主归属和文章类型；
4. 选择保留原 ID 的主文章；
5. 为新文章分配新 ID；
6. 移动正文而不是复制；
7. 更新 MOC、路线、Manifest、来源和反向链接；
8. 运行校验并抽查历史链接。

# 6. 文章合并与唯一主解释

## 6.1 需要合并的信号

- 两篇文章在相同抽象层回答同一个问题；
- 定义、推导和例子大量重复；
- 只是因为来自不同来源或项目而各写一版；
- 两篇文章的更新总是需要同步；
- 读者无法判断哪篇是权威主版本。

## 6.2 主版本选择

优先保留：

1. 主归属正确的文章；
2. 稳定 ID 已被更多内容引用的文章；
3. 来源、推导和验证更完整的文章；
4. 标题和问题边界更清晰的文章。

## 6.3 合并后的旧文章

- `seed`／`outline`、无稳定引用的重复文章：合并后删除；
- 已有稳定 ID、项目链接、外部引用或历史价值：保留最小替代页；
- 替代页使用 `lifecycle: deprecated` 和 `superseded_by`；
- 替代页只说明原问题、替代原因和新文章，不继续维护完整正文。

## 6.4 唯一主解释

通用基础解释放在最基础的主归属领域。应用文章只能：

- 简短回顾必要定义；
- 链接基础文章；
- 展开领域特有约定、数据流、API、实现、性能和失败条件；
- 不复制完整基础推导。

# 7. 稳定 ID

## 7.1 ID 格式

```text
<DOMAIN>-<MODULE>-<NNN>
<DOMAIN>-<CATEGORY>-<MODULE>-<NNN>
```

示例：

```text
MATH-LA-001
GFX-PROJ-002
GFX-EXP-TRANSFORM-001
```

允许格式由大写字母、数字和连字符组成，最后一段为三位数字，总段数为 3～5。

## 7.2 领域前缀

```text
MATH   数学
PHYS   物理与工程科学
CS     计算机科学
GFX    图形学与渲染
AI     人工智能与数据科学
SWE    软件工程
SYS    系统与平台
ENG    游戏引擎与实时应用
MEDIA  音视频与多媒体
ROB    嵌入式、机器人与智能驾驶
DESIGN 设计、摄影与内容创作
BIZ    产品、商业与职业发展
HUM    人文与社会科学
KB     知识库系统
```

## 7.3 稳定性原则

- ID 一旦被 Manifest、项目、输出或其他文章引用，原则上不修改；
- 标题、文件名、目录和主归属调整时保留 ID；
- ID 不是当前目录层级的强编码，只是稳定身份；
- 只有错误分配、碰撞或两个对象被错误视为同一对象时才允许变更 ID；
- ID 变更必须记录旧 ID 和迁移映射。

## 7.4 迁移 ID

从旧知识库迁入时使用：

```yaml
legacy_ids:
  - OLD-GFX-102
  - legacy/path/note-name
```

多个旧文章合并为一个主版本时，可以保留多个 `legacy_ids`。旧 ID 不参与新 ID 唯一性判断，但不得在多个新文章中重复声明。

# 8. 标题、文件名、别名和重命名

## 8.1 标题和文件名

- 标题表达当前最清晰的问题或对象名；
- 文件名默认与一级标题一致；
- 不在文件名中加入“最终版”“学习笔记”“详细介绍”等状态词；
- 文章文件名不使用 ID 前缀，ID 保存在 Frontmatter；
- 应用文章在标题中加入必要上下文，例如“傅里叶分析在纹理过滤中的应用”。

## 8.2 `aliases`

`aliases` 只用于：

- 常用中英文名称；
- 行业内稳定缩写；
- 重命名前仍可能被搜索的旧标题；
- 同义但不适合作为主标题的术语。

规则：

- 使用 YAML 列表；
- 不重复当前标题；
- 不收录拼写错误和一次性措辞；
- 不把标签和上位分类放入别名；
- 通常控制在 1～8 个。

## 8.3 重命名流程

1. 修改文件名和一级标题；
2. 保留稳定 ID；
3. 由 Obsidian 更新 WikiLink；
4. 有搜索价值时把旧标题加入 `aliases`；
5. 更新 Manifest `path`；
6. 运行链接和一致性校验；
7. 若存在外部路径引用，保留替代页或发布重定向。

# 9. Properties、标签、正文链接和目录

## 9.1 目录

目录只回答：

> 这篇文章的稳定主归属是什么？

目录不表达状态、学习顺序、所有关系或当前优先级。

## 9.2 Properties

Properties 保存机器查询和校验需要的信息：

```text
id
type
domain
maturity
verification
lifecycle
map_kind
status
platforms
apis
versions
legacy_ids
superseded_by
```

不维护与正文重复的巨大 `related` 列表。

## 9.3 正文链接

WikiLink 保存需要人理解的语义关系：

- 前置知识；
- 上层应用；
- 对比和边界；
- 实现与实验；
- 来源和证据；
- 替代和演化；
- 项目、输出和责任领域中的使用关系。

关键关系应出现在有解释的正文中，而不只是无语义列表。

## 9.4 标签

本系统不要求任何全局标签。标签不能替代：

- 目录中的知识领域；
- `type`；
- `maturity`、`status` 或 `lifecycle`；
- `platforms`、`apis` 和 `versions`；
- MOC 和学习路线。

标签只允许用于临时、跨领域、尚未值得建立正式字段的检索标记。一个标签长期出现在 10 篇以上笔记，或影响自动化和治理时，应升级为 Property、索引或 MOC。

禁止建立大规模层级标签树。

# 10. 导航对象协作

## 10.1 MOC

MOC 是人工策展的主题知识网络：

- 解释主题边界；
- 选择核心文章；
- 展示前置、分支、应用、对比和实验；
- 允许提到未建设主题，但不创建失效链接；
- 不追求收录每篇文章。

## 10.2 学习路线

学习路线围绕明确目标、受众和完成标准组织顺序：

- 可以跨领域；
- 同一文章可出现在多条路线；
- 包含阶段、练习、检查点和退出标准；
- 不复制 MOC 对主题边界的完整解释。

## 10.3 索引

索引提供快速查找：

- 尽量完整；
- 条目保持简洁；
- 可以按术语、算法、API、实验、故障等维度生成；
- 不负责解释关系和顺序。

## 10.4 仪表盘

仪表盘展示动态状态和行动入口：

- 待处理；
- 待验证；
- 待更新；
- 正在阅读；
- 活跃项目；
- 近期输出。

仪表盘应尽量使用查询，不人工维护与其他页面重复的清单。

## 10.5 Manifest

Manifest 负责建设计划和机器状态：

- 计划中的主题可以没有实体文件；
- 从 `seed` 开始必须有路径；
- 已实例化主题的 `status` 与文章 `maturity` 对齐；
- 依赖使用稳定 ID；
- A/B/C 优先级属于具体路线或批次；
- 不要求把所有临时、输出或来源笔记登记进去。

## 10.6 查找优先顺序

```text
不知道放哪里       → 信息归属规则
想理解一个主题     → MOC
想按顺序学习       → 学习路线
知道名称想快速找   → 索引／搜索
想看当前状态       → 仪表盘
想看未来建设计划   → Manifest
想知道正式解释     → 知识文章
```

# 11. 跨领域知识

## 11.1 主归属

跨领域主题仍只有一个基础主文章，放在能脱离应用上下文后仍然成立的最基础领域。

例如：

```text
矩阵与线性映射              → 数学
GPU 并行体系结构基础        → 计算机科学
GPU 渲染管线                → 图形学
UE5 RDG                      → 游戏引擎与实时应用
FFmpeg 时间戳与同步         → 音视频与多媒体
异步任务系统工程设计        → 软件工程
```

## 11.2 应用文章

应用文章：

- 标题中说明应用上下文；
- 链接基础文章；
- 只展开本领域特有语义、约定、实现和失败条件；
- 可以有独立 ID、来源、成熟度和验证证据；
- 不复制基础文章的完整定义和推导。

## 11.3 跨领域 MOC

跨领域 MOC 放在 `99 跨领域知识地图`，用于组织一个问题涉及的多个主归属文章，例如：

- 实时渲染器工程；
- 智能驾驶可视化；
- AI 辅助内容生产；
- 音视频 GPU 加速。

跨领域 MOC 不创建新的知识领域，也不拥有基础解释。

# 12. 知识对象状态转换

## 12.1 建设成熟度

```text
planned（仅 Manifest）
   ↓ 实例化
seed
   ↓ 明确问题和范围
outline
   ↓ 完成主体和证据入口
draft
   ↓ 审核、验证和实际使用
stable
   ↓ 长期复用、多次修订和冲突处理
evergreen
```

允许降级。例如新证据推翻关键结论时，可以从 `stable` 降为 `draft`，并在变更记录中说明原因。

## 12.2 生命周期

```text
active
  ↓ 发现版本或证据问题
needs-update
  ├─ 修正完成 → active
  └─ 不再适用 → deprecated

deprecated
  ├─ 被新文章替代 → 保留替代页
  ├─ 重新有效 → active
  └─ 退出知识网络 → archived（少见）
```

## 12.3 验证证据

验证证据不构成单向等级。可以累积，也可以在证据失效时移除：

```text
source-checked
derived
experiment-reproduced
production-validated
```

移除证据时应说明失效原因，并重新评估成熟度。

# 13. 废弃、替代和历史保护

## 13.1 `needs-update`

适用于：

- 来源或版本已经变化；
- 发现局部错误；
- 关键链接失效；
- 实验无法复现；
- 文章仍有价值但需要修订。

## 13.2 `deprecated`

适用于：

- 整体模型已被新模型替代；
- API 或实现已经退出支持范围；
- 内容被合并到更完整主文章；
- 继续维护会制造重复或误导。

需要：

```yaml
lifecycle: deprecated
superseded_by:
  - "[[替代文章]]"
```

正文顶部说明：

- 为什么过时；
- 从什么版本或时间开始；
- 替代文章是什么；
- 哪些历史场景仍然适用。

## 13.3 删除

可以直接删除：

- 无稳定 ID 和入站链接的 `seed`／`outline` 重复笔记；
- 无长期价值的临时碎片；
- 已经完整合并且不需要保留路径的草稿。

Git 历史不是保留无价值空壳的理由。
