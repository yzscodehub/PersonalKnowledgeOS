# D4 全知识领域蓝图

## 1. 目标

D4 为个人知识库中的全部知识领域建立稳定蓝图，使未来新增常见主题时能够判断：

```text
主归属属于哪个知识领域
应进入哪个一级模块
需要链接哪些基础领域
适合使用什么来源与验证方式
应建立哪类 MOC、学习路线或实验
首批建设从哪里开始
哪些内容明确不属于该领域
```

蓝图是**建设规划和边界说明**，不是知识正文，也不要求立即创建对应目录和文章。

# 3. 蓝图统一结构

每个领域蓝图必须包含：

1. **领域目标**：该领域长期解释和维护什么；
2. **主归属边界**：哪些内容进入，哪些内容转交相邻领域；
3. **一级模块**：稳定逻辑模块及模块代码；
4. **核心基础**：进入该领域前最重要的前置；
5. **典型应用**：能够产生什么工程、学习或输出结果；
6. **来源与证据**：适合的来源类型和验证方式；
7. **实验与实践**：如何避免只做文本整理；
8. **核心 MOC**：未来应维护的主题网络；
9. **跨领域关系**：与其他领域如何复用和分工；
10. **首批建设建议**：完整设计合并后的起步顺序；
11. **非目标**：明确阻止范围无限扩张。

# 4. 模块与目录的关系

领域蓝图中的一级模块首先是**逻辑模块**，不自动等于实体目录。

只有满足以下任一条件时才创建模块目录：

- 已有至少 3 篇正式文章；
- 已经确认一批近期建设主题；
- 需要一个稳定 MOC 或学习路线承载该模块；
- 迁移批次已经批准，并需要确定目标路径。

否则模块只保留在：

```text
领域蓝图
Manifest
学习路线
MOC 的“尚未建设”部分
```

不通过批量创建空目录表示蓝图完成。

# 5. 领域间复用顺序

跨领域主题优先按抽象层拆分：

```text
数学／物理基础
    ↓
计算机科学一般原理
    ↓
图形学、AI、音视频、机器人等领域方法
    ↓
软件工程通用实现方法
    ↓
系统平台与具体工具链
    ↓
引擎、框架和业务应用
```

该顺序不是价值等级，而是避免重复解释的主归属判定工具。

例如 GPU 主题：

```text
03 计算机科学      GPU 并行体系结构
04 图形学与渲染    图形管线和渲染工作负载
05 人工智能        张量计算与推理工作负载
07 系统与平台      CUDA、驱动、分析工具和部署
08 游戏引擎        UE5／Unity 中的 GPU 资源和任务映射
```

# 7. 核心 MOC 分层

每个知识领域未来通常维护三层导航：

```text
领域总览 MOC
    ↓
模块 MOC
    ↓
问题型或应用型 MOC
```

规则：

- 领域总览只解释领域结构和入口；
- 模块 MOC 组织稳定主题网络；
- 问题型 MOC 可以跨模块或跨领域；
- 学习路线根据具体目标排序，不复制总览；
- 索引负责查找，不承担教学结构；
- 尚未实例化的 MOC 名称只在蓝图中用普通文本记录。

---

# 8. 来源和实践共同驱动

领域建设不能只依赖收藏资料。每个领域应形成：

```text
权威来源或原始资料
+ 可解释的正式知识
+ 与领域匹配的练习、实验、实现或案例
+ 项目和输出中的实际使用
```

不同领域的验证方式不同：

- 数学：证明、推导、反例和数值检查；
- 物理：模型假设、量纲、实验和工程测量；
- 计算机科学：证明、复杂度分析、模拟和参考实现；
- 工程领域：测试、基准、捕获、日志和生产记录；
- 设计与人文领域：案例分析、作品实践、来源比较和批评性论证。

---

# 9. 跨领域地图

跨领域地图解决真实目标，不建立新的含糊顶层领域。优先规划：

```text
数学到图形学
实时渲染器工程
GPU 工作负载与性能分析
游戏引擎渲染架构
智能驾驶三维可视化
音视频与 GPU 加速
AI 辅助知识生产
神经渲染
机器人坐标、定位与可视化
个人技术职业能力地图
```

详细规则见 [[80 系统/50 领域蓝图/99 跨领域知识地图蓝图|99 跨领域知识地图蓝图]]。
