# D1 顶层信息角色详细设计

## 1. 目标

D1 负责把顶层目录从“名称正确”推进到“可以日常运行”。每个角色必须明确：

```text
负责什么
什么内容可以进入
什么内容不能进入
进入时记录什么状态
日常如何处理和回顾
满足什么条件后离开
离开后去哪里
异常时如何恢复
```

D1 不设计具体知识文章原型，也不展开完整端到端工作流；这些分别属于 D2 和 D3。

---

# 2. 顶层角色总览

| 角色 | 核心问题 | 时间特征 | 主要状态载体 | 典型离开方式 |
|---|---|---|---|---|
| `00 收件箱` | 这条信息是什么、应该去哪里？ | 临时 | `status`、`capture_type` | 分流、删除 |
| `10 项目` | 要交付什么结果，如何完成？ | 有结束条件 | `status`、下一步、里程碑 | 复盘后归档 |
| `20 责任领域` | 什么标准需要长期维持？ | 长期持续 | `status`、健康度、风险 | 退休后归档 |
| `30 知识` | 什么解释值得长期复用？ | 长期演进 | `maturity`、`verification`、`lifecycle` | 合并、替代、废弃 |
| `40 来源` | 结论来自哪里，能支持什么声明？ | 阅读／参考周期 | `status`、版本、定位 | 处理完成或归档 |
| `50 输出` | 面向谁交付什么成品？ | 有发布或交付节点 | `status`、版本、平台 | 保留、退役或归档 |
| `60 日记与回顾` | 什么时候发生了什么，下一步是什么？ | 时间序列 | 日期、回顾周期 | 提炼后保留历史 |
| `80 系统` | 知识库自身如何设计和运行？ | 长期治理 | ADR、规则、版本 | 被新规则取代 |
| `90 档案` | 哪些内容退出日常视图但需要保留？ | 历史 | 原角色状态、归档日期 | 恢复到原角色 |

## 2.1 公共原则

1. **单一主归属**：每个笔记只有一个稳定主目录；其他关系用链接表达。
2. **状态不驱动搬家**：进行中、等待、待验证等状态使用 Properties，不创建状态文件夹。
3. **收件箱只做缓冲**：不因暂时无法判断而丢失信息，也不让收件箱成为永久仓库。
4. **项目与输出分离**：项目管理生产过程，输出保存可长期使用的交付物。
5. **责任与知识分离**：责任领域管理标准和健康度，知识领域保存可复用解释。
6. **来源与知识分离**：来源保存证据入口，正式知识保存重组后的解释。
7. **日记与知识分离**：时间记录保留过程，稳定结论提炼到其他角色。
8. **档案不等于删除**：档案保存历史和恢复能力；无长期价值的内容直接删除。
9. **公开安全优先**：当前仓库公开，私人、敏感、雇佣机密和无权公开内容不得进入任何角色。

# 3. `00 收件箱`

## 3.1 职责

收件箱是未完成分类的信息缓冲层，解决“先捕捉，后判断”的问题。

它可以接收：

- 临时问题；
- 想法和灵感；
- 待阅读链接或书目；
- 待办线索；
- 项目或知识主题候选；
- 一段暂时不知道如何处理的笔记；
- 需要进一步澄清的记录。

它不负责：

- 长期保存资料；
- 管理复杂任务；
- 撰写正式知识正文；
- 保存敏感信息；
- 代替日记记录日常过程。

## 3.2 捕捉类型

```text
question       问题
idea           想法
action         行动线索
source         来源线索
observation    观察
reference      临时参考
decision       待确认决策
unknown        暂时无法判断
```

## 3.3 状态模型

```text
unprocessed → clarify → routed
           ↘ discarded
```

- `unprocessed`：尚未处理；
- `clarify`：缺少上下文，等待补充；
- `routed`：已经移动或转写到正式角色；
- `discarded`：确认不需要保留。

已完成分流的独立捕捉笔记应删除或移动，不长期保留 `routed` 空壳。

## 3.4 处理时限

- 明确紧急行动：当天进入项目或外部任务系统；
- 普通捕捉：一周内处理；
- 连续两次周回顾仍无法判断：补充上下文、转为明确问题或删除；
- 超过 30 天未处理：默认视为低价值，除非能说明保留理由。

## 3.5 分流动作

处理一条收件箱内容时，只做以下动作之一：

```text
创建／更新项目
创建／更新责任领域
提炼为知识问题或正式知识
创建来源笔记
创建输出草稿
写入当天日记或阶段回顾
移动到档案
删除
```

## 3.6 失败保护

- 无法判断时保留原始上下文，不强行分类；
- 外部链接至少记录标题和一句用途，避免只保存裸 URL；
- 涉及凭据和私人信息时不进入公开仓库；
- 同一主题的多条碎片优先合并到一个处理条目；
- 收件箱清理失败时，先处理可在两分钟内完成的条目，再处理复杂内容。

## 3.7 模板与回顾

- 模板：[[80 系统/20 模板/收件箱条目模板|收件箱条目模板]]；
- 回顾：每日快速浏览，周回顾清空或明确剩余条目；
- 退出条件：所有条目都已分流、删除或明确进入 `clarify`。

# 4. `10 项目`

## 4.1 项目定义

满足以下条件才建立项目：

- 有明确预期成果；
- 有完成条件或阶段边界；
- 需要多步行动；
- 需要持续跟踪决策、材料或进度。

单一动作不是项目；没有结束日期但需要长期维护的内容属于责任领域；稳定解释属于知识。

## 4.2 项目状态机

```text
planned → active → completed
          ↓   ↑
       waiting
          ↓
        paused

任意未完成状态 → cancelled
```

- `planned`：已定义成果，但尚未投入；
- `active`：当前正在推进；
- `waiting`：下一步依赖外部事件或他人；
- `paused`：主动停止，暂不承诺近期继续；
- `completed`：完成条件全部满足；
- `cancelled`：决定不再完成原成果。

## 4.3 项目主页最小要求

每个项目必须能够快速回答：

```text
预期成果是什么
完成条件是什么
当前状态是什么
下一步行动是什么
主要风险和依赖是什么
相关知识、来源和输出在哪里
```

`active` 项目必须至少有一个明确下一步行动。`waiting` 项目必须记录等待对象和复查日期。

## 4.4 项目内容边界

项目内可以保存：

- 项目主页；
- 计划、里程碑和决策；
- 项目专属实验和会议记录；
- 尚未稳定的实现笔记；
- 交付物草稿链接。

项目内不长期复制：

- 已经稳定的正式知识；
- 通用来源正文；
- 已发布输出的唯一副本；
- 与项目无关的长期责任说明。

## 4.5 完成和归档

项目进入 `completed` 或 `cancelled` 前必须完成最小复盘：

- 实际结果；
- 完成／取消原因；
- 关键决策；
- 可复用知识；
- 可长期保留输出；
- 未完成事项去向；
- 后续项目或责任领域更新。

完成复盘后整体移动到：

```text
90 档案/10 项目/<年份>/<项目名称>/
```

## 4.6 回顾频率

- `active`：每周；
- `waiting`：按复查日期，至少每周查看；
- `paused`：每月决定恢复、继续暂停或取消；
- `planned`：每月清理，防止无限积压。

## 4.7 模板

- [[80 系统/20 模板/项目主页模板|项目主页模板]]；
- 项目复盘直接使用项目主页的“复盘”章节，不额外制造重复文档。

# 5. `20 责任领域`

## 5.1 职责

责任领域表示需要长期维持标准的责任范围，没有天然完成日期。

典型公开安全示例：

- 职业与技术能力；
- 学习与知识管理；
- 内容创作与个人品牌；
- 数字设备与数据管理。

当前公开仓库不记录私人健康、财务或家庭细节；未来仓库转为私有后再启用相关责任领域。

## 5.2 状态模型

```text
active
watch
at-risk
paused
retired
```

- `active`：按既定标准持续维护；
- `watch`：当前无明显问题，但需要重点观察；
- `at-risk`：已低于标准或存在明确风险；
- `paused`：暂时不投入维护，但责任尚未终止；
- `retired`：责任已经结束，准备归档。

可选健康度：

```text
5  明显高于标准
4  达到标准
3  基本可接受
2  低于标准，需要项目修复
1  严重失衡，需要立即处理
```

健康度只用于趋势判断，不追求精确量化。

## 5.3 责任领域主页

至少包含：

- 责任范围和非目标；
- 维护标准；
- 当前状态和健康度；
- 关键指标或观察信号；
- 例行维护；
- 风险和触发条件；
- 关联项目；
- 关联知识领域；
- 最近回顾和下一次回顾日期。

## 5.4 项目触发规则

责任领域出现以下情况时建立项目：

- 健康度持续低于 `3`；
- 需要一次性达到明确结果；
- 风险需要多步修复；
- 需要建立新系统、作品或能力；
- 例行维护无法解决问题。

项目完成后更新责任领域的标准、状态或例行机制。

## 5.5 回顾与退休

- 活跃责任领域：每月回顾；
- 高风险领域：每周或按触发条件检查；
- 每季度检查标准是否仍然合理；
- 责任永久结束时标记 `retired`，完成最终回顾后移动到 `90 档案/20 责任领域/`。

## 5.6 模板

- [[80 系统/20 模板/责任领域主页模板|责任领域主页模板]]。

# 6. `30 知识`

## 6.1 准入条件

内容进入正式知识前，应满足至少一个条件：

- 可以脱离当前日期或项目独立解释；
- 会被多个项目、输出或领域复用；
- 值得长期维护定义、推导、机制或边界；
- 已经形成可验证的稳定问题；
- 需要成为其他文章的基础前置。

只有线索、摘录或阅读摘要时，先保留在收件箱、来源或项目中。

## 6.2 角色内状态

知识使用三套独立状态：

```text
maturity      seed → outline → draft → stable → evergreen
verification  多证据列表
lifecycle     active / needs-update / deprecated / archived
```

具体文章类型、拆分和导航属于 D2。

## 6.3 拆分与合并原则

- 一篇文章解决一个稳定问题；
- 同一基础概念只有一个完整主解释；
- 平台、引擎和业务上下文建立应用文章；
- 来源不同不构成拆分理由；
- 学习路线不同不构成复制理由；
- 两篇文章长期解释同一问题时，应选择主版本并合并。

## 6.4 废弃与历史

正式知识通常保留原路径，不整体移动到档案：

```yaml
lifecycle: deprecated
superseded_by:
  - "[[替代文章]]"
```

只有确认不再参与知识网络、没有历史链接价值的特殊内容才进入 `90 档案/30 知识历史/`。

## 6.5 回顾触发

知识不要求按固定周期逐篇检查，优先在以下时机复核：

- 被项目或输出使用；
- 来源或版本发生变化；
- 自动化标记 `needs-update`；
- 出现冲突证据；
- 进入更高成熟度前；
- 对应 API、平台或产品进入新版本。

## 6.6 模板与入口

- [[80 系统/20 模板/知识文章模板|知识文章模板]]；
- [[30 知识/00 知识总览|知识总览]]；
- 详细对象模型将在 D2 冻结。

# 7. `40 来源`

## 7.1 职责

来源笔记回答：

```text
这是什么来源
哪个版本
为什么阅读
可以支持什么声明
重要内容在哪里
有哪些限制
已经提炼出什么知识
```

来源不是正式知识正文，也不是原始文件仓库。

## 7.2 状态模型

```text
unread → reading → processed
   ↘        ↘
 reference  abandoned
```

- `unread`：已登记，尚未系统处理；
- `reading`：正在阅读或提炼；
- `processed`：本轮目标已完成，关键内容已提炼；
- `reference`：不计划完整处理，只作长期查阅；
- `abandoned`：决定停止阅读，并记录原因。

`processed` 不代表来源永远完成；新的问题可以重新进入阅读状态。

## 7.3 来源处理要求

来源进入 `processed` 前至少完成：

- 版本和书目信息；
- 阅读目的；
- 可支持的声明类型；
- 关键章节、页码、提交或 URL 定位；
- 限制和适用范围；
- 已提炼知识的反向链接；
- 权利、许可和原始文件存储说明。

## 7.4 阅读优先级

来源优先级不写成永久权威等级，而由当前项目、学习路线或问题上下文决定。正式结论按声明类型选择证据。

## 7.5 归档

- 长期参考来源一般保留原路径并标记 `reference` 或 `processed`；
- 低价值、重复或停止使用的来源可以移动到 `90 档案/40 来源/`；
- 原始书籍、视频和大型文件不随来源笔记归档到 Git 仓库。

## 7.6 模板与回顾

- [[80 系统/20 模板/来源笔记模板|来源笔记模板]]；
- 每周检查正在阅读来源；
- 每月清理长期 `unread` 列表；
- 阅读与提炼的完整流程属于 D3。

# 8. `50 输出`

## 8.1 职责

输出是面向明确受众、具有交付形式的成果，例如：

- 技术文章；
- 教程或课程；
- 视频脚本；
- 演示文稿；
- 面试材料；
- 社交媒体内容；
- 可公开的项目文档。

项目管理生产过程；输出保存可继续使用、发布和维护的交付物。

## 8.2 状态模型

```text
idea → draft → review → ready → published
  ↘                         ↘
 cancelled                  retired
```

- `idea`：只有输出设想，不一定立即生产；
- `draft`：正在形成内容；
- `review`：结构或事实等待审核；
- `ready`：可以交付或发布；
- `published`：已经发布或交付；
- `retired`：不再主动维护，但保留历史版本；
- `cancelled`：决定不继续。

## 8.3 输出主页

至少记录：

- 目标受众和用途；
- 核心信息；
- 形式和平台；
- 关联项目；
- 使用的知识和来源；
- 当前状态；
- 版本和发布记录；
- 发布后反馈；
- 需要回流知识库的修正。

## 8.4 平台适配

一个输出主题可以有一个规范主版本和多个平台变体：

```text
主题主页
├── 长文主版本
├── 小红书版本
├── 视频脚本
└── 演示文稿
```

平台变体共享核心结论，但可以调整标题、长度、语气和媒介结构。

## 8.5 输出完成后的知识回流

发布或交付后必须检查：

- 是否发现事实错误；
- 是否出现新的解释方式；
- 读者问题是否暴露知识缺口；
- 是否需要更新来源和验证证据；
- 是否产生新的项目或知识主题。

## 8.6 归档和保留

- 已发布且仍有价值的输出保留在 `50 输出`；
- 已过时但需要历史链接的内容标记 `retired`；
- 取消或失去长期价值的输出移动到 `90 档案/50 输出/`；
- 发布平台不是唯一副本，仓库保存可维护主版本或必要元数据。

# 9. `60 日记与回顾`

## 9.1 职责

时间型笔记记录过程、上下文、变化和决策时点，不承担稳定知识正文。

建议结构：

```text
10 每日笔记
20 每周回顾
30 月度回顾
40 季度与年度回顾
50 阶段复盘
```

目录只在真正开始使用对应周期时创建，不提前制造空目录。

## 9.2 每日笔记

每日笔记可以记录：

- 当天重点；
- 项目进展和阻塞；
- 临时观察；
- 收件箱线索；
- 当天决策；
- 需要在周回顾处理的问题。

不要把正式知识完整写在每日笔记中；通过链接指向或在回顾时提炼。

## 9.3 周回顾

周回顾是系统最重要的运行节奏，至少完成：

- 清理收件箱；
- 检查所有活跃项目的下一步；
- 检查等待和暂停项目；
- 查看责任领域风险；
- 处理正在阅读来源；
- 提炼本周稳定知识；
- 更新输出状态；
- 归档已完成内容；
- 确定下一周重点。

## 9.4 月度和阶段回顾

月度回顾关注趋势和系统层调整：

- 责任领域健康度；
- 项目组合是否过载；
- 学习和输出是否产生结果；
- 知识库维护成本；
- 需要停止、合并或归档的内容。

阶段复盘用于项目阶段、设计阶段或迁移批次结束，不替代项目复盘。

## 9.5 提炼规则

回顾中发现的内容按角色回流：

- 行动和成果 → 项目；
- 长期标准和风险 → 责任领域；
- 稳定解释 → 知识；
- 证据入口 → 来源；
- 可交付内容 → 输出；
- 已结束历史 → 档案。

# 10. `80 系统`

## 10.1 职责

系统目录保存知识库自身的设计和运行机制：

- 总体设计和路线图；
- 治理规则；
- 模板；
- Manifest；
- 索引定义；
- 自动化和脚本说明；
- ADR；
- Obsidian 与 Git 约定；
- CHANGELOG；
- 阶段评审与设计演练。

业务知识和普通项目不得放在系统目录。

## 10.2 变更规则

- 影响长期结构的决定必须形成 ADR；
- 小型说明修正直接更新规则；
- 系统设计不能由单个内容项目临时改变；
- 新规则必须同步模板、脚本、主页和 CHANGELOG；
- 被取代规则保留历史状态和替代关系。

系统目录的完整治理在 D6、D7 和 D9 继续完善。

# 11. `90 档案`

## 11.1 职责

档案保存退出日常视图但仍有历史、证据或恢复价值的内容。

可以归档：

- 已完成、取消或长期停止的项目；
- 已退休的责任领域；
- 低频且不再维护的来源；
- 取消或退役的输出；
- 旧系统版本、迁移批次和历史设计；
- 特殊情况下退出知识网络的历史知识。

不应归档：

- 只是暂时没有使用的稳定知识；
- 仍需要维护的责任领域；
- 正在等待外部事件的项目；
- 没有长期价值、本应删除的垃圾内容。

## 11.2 目录建议

```text
90 档案/
├── 10 项目/
├── 20 责任领域/
├── 30 知识历史/
├── 40 来源/
├── 50 输出/
├── 60 日记与回顾/
└── 80 系统历史/
```

只在出现真实档案时创建对应目录。

## 11.3 只读约定

归档内容原则上只读，允许的修改包括：

- 修复失效内部链接；
- 补充归档日期和原因；
- 增加恢复或替代关系；
- 隐私和版权修复；
- 必要的格式迁移。

不得在档案中继续日常推进项目或维护正文。

## 11.4 恢复流程

恢复时：

1. 确认重新激活的原因；
2. 恢复到原角色目录，而不是在档案中继续编辑；
3. 更新状态、日期和下一步；
4. 检查链接、来源和附件；
5. 在原档案位置留下恢复说明或依赖 Git 历史追踪。

# 12. 统一信息归属决策树

```text
新信息
  │
  ├─ 当前无法判断？
  │      └─ 00 收件箱
  │
  ├─ 有明确成果、完成条件且需要多步推进？
  │      └─ 10 项目
  │
  ├─ 是需要长期维护的责任、标准或风险？
  │      └─ 20 责任领域
  │
  ├─ 是可脱离当前上下文复用的解释、模型或方法？
  │      └─ 30 知识
  │
  ├─ 主要价值是出处、版本、章节、数据或证据入口？
  │      └─ 40 来源
  │
  ├─ 面向明确受众并具有交付形式？
  │      └─ 50 输出
  │
  ├─ 主要价值是记录某天、某周或某阶段的过程？
  │      └─ 60 日记与回顾
  │
  ├─ 是知识库自身的规则、模板、决策或自动化？
  │      └─ 80 系统
  │
  ├─ 已退出日常维护但需要保留历史或恢复能力？
  │      └─ 90 档案
  │
  └─ 没有长期价值？
         └─ 删除
```

## 12.1 一分钟判断法

仍然犹豫时，先写一句话补全：

```text
我保留它，是为了 ______。
```

- 为了完成一个结果 → 项目；
- 为了长期维持标准 → 责任领域；
- 为了以后理解和复用 → 知识；
- 为了追踪证据 → 来源；
- 为了交付给别人 → 输出；
- 为了保留时间上下文 → 日记；
- 为了管理知识库本身 → 系统；
- 为了保留历史和恢复 → 档案；
- 无法补全 → 收件箱或删除。

# 13. 边界案例

| 内容 | 主归属 | 原因 |
|---|---|---|
| “学习 Vulkan” | 不直接建笔记 | 需要先明确是项目、路线还是知识主题 |
| 三个月完成 Vulkan 入门 Demo | 项目 | 有结果和完成条件 |
| Vulkan Pipeline Barrier 语义 | 知识 | 可复用的 API 解释 |
| Vulkan 规范某章节 | 来源 | 证据入口 |
| Vulkan 教程文章草稿 | 输出 | 面向读者的交付物 |
| 每天学习 Vulkan 的记录 | 日记 | 时间过程 |
| 保持图形学职业竞争力 | 责任领域 | 长期维护标准 |
| 一次面试准备 | 项目 | 有明确截止和成果 |
| 面试知识清单 | 输出或学习路线 | 取决于是否面向交付或学习顺序 |
| 一个 Bug 的临时日志 | 项目 | 仍在排查和修复 |
| 已稳定的 Bug 根因与修复模式 | 知识 | 可复用故障知识 |
| 一本书的逐章笔记 | 来源 | 仍按来源结构组织 |
| 从多本书重组出的矩阵解释 | 知识 | 已脱离单一来源 |
| 视频制作过程 | 项目 | 管理生产活动 |
| 最终视频脚本 | 输出 | 长期交付物 |
| 已完成项目的过程文件 | 档案 | 退出日常视图但需保留 |
| 已过时知识文章 | 原知识路径 | 使用 deprecated 和替代关系，不默认归档 |
| 没有上下文的截图 | 收件箱或删除 | 先判断用途，无法判断则删除 |
