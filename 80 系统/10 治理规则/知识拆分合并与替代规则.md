# 知识拆分、合并与替代规则

## 目标

控制文章粒度，保证一个稳定问题只有一个完整主解释，同时允许应用文章、历史文章和不同导航视角共存。

## 核心问题测试

为文章写一句话：

> 本文主要回答：________。

无法用一个稳定问题概括，通常表示需要拆分；两篇文章用同一句话概括，通常表示需要合并或明确主从关系。

## 应当拆分的情况

- 同时回答两个能够独立复用的核心问题；
- 两部分具有不同前置知识；
- 两部分需要不同验证方式；
- 两部分有不同生命周期或版本敏感性；
- 通用理论与具体平台实现混在一起；
- 稳定概念与版本敏感 API 混在一起；
- 故障案例中的根因已经形成通用机制；
- 更新其中一部分经常迫使无关内容一起修改。

## 不应拆分的理由

- 来源来自不同书籍或论文；
- 同一文章出现在不同学习路线；
- 文章较长但仍回答同一个问题；
- 同一原理被多个项目使用；
- 为了让目录看起来更细；
- 不同 API 共享同一基础理论。

## 拆分流程

1. 明确原文章主问题；
2. 写出候选文章各自的主问题；
3. 确定每篇的主归属和 `type`；
4. 选择保留原 `id` 的主文章；
5. 为新增对象分配新 ID；
6. 移动正文，不复制正文；
7. 更新来源、MOC、路线、Manifest 和反向链接；
8. 运行校验并抽查历史链接。

## 需要合并的信号

- 两篇文章在同一抽象层回答同一问题；
- 定义、推导和例子大量重复；
- 只是因为来源、项目或平台不同而各写一版；
- 更新时总需要同步修改；
- 读者无法判断哪篇是主版本；
- 两篇文章的链接网络和使用场景高度重合。

## 主版本选择

按以下顺序判断：

1. 主归属是否正确；
2. 稳定 ID 是否已被广泛引用；
3. 问题和边界是否更清晰；
4. 来源、推导和验证是否更完整；
5. 标题是否更稳定；
6. 是否更适合作为其他文章的前置。

## 合并后的旧文章

### 可以删除

- `seed` 或 `outline`；
- 无稳定入站链接；
- 没有外部路径引用；
- 没有独立历史价值；
- 内容已经完整迁入主版本。

### 应保留替代页

- 已有稳定 ID；
- 被项目、输出、来源或其他知识引用；
- 可能存在外部路径链接；
- 代表旧版本或历史模型；
- 删除会让读者无法理解历史决策。

替代页示例：

```yaml
---
id: GFX-OLD-001
type: concept
domain: graphics
maturity: stable
lifecycle: deprecated
superseded_by:
  - "[[新主文章]]"
---
```

正文只保留：

- 原文章解决的问题；
- 被替代原因；
- 替代文章；
- 仍然适用的历史范围。

不得继续维护两份完整正文。

## 唯一主解释

### 基础文章

负责：

- 完整定义；
- 通用推导；
- 与应用无关的机制；
- 稳定边界和反例。

### 应用文章

负责：

- 应用上下文；
- 平台或领域约定；
- API、数据流和实现；
- 性能、调试和失败条件；
- 对基础文章的必要短回顾和链接。

应用文章不得重新维护基础文章的完整定义与推导。

## 跨领域规则

- 基础主文章放在移除应用上下文后仍然成立的最基础领域；
- 应用文章放在使用该知识解决问题的领域；
- 跨领域 MOC 只组织现有文章；
- 不为跨领域主题新建含糊的顶层领域；
- 同一实现可链接多个基础文章，但仍只有一个主归属。

## 过时和更新

### `needs-update`

用于仍有价值但需要修订的文章：

- 版本变化；
- 局部错误；
- 实验不能复现；
- 来源失效；
- 存在冲突证据。

### `deprecated`

用于整体不再推荐或已被替代的文章。原则上需要 `superseded_by`。确实没有替代文章时，正文必须明确写出弃用原因、仍适用范围和历史保留价值。

### `archived`

正式知识很少使用。只有退出知识网络、无需继续参与导航但仍需保存历史时才使用，并通常移动到 `90 档案/30 知识历史/`。

## 合并检查清单

- [ ] 主版本和主 ID 已确定；
- [ ] 正文已经移动而非复制；
- [ ] 旧版本已经删除或改为替代页；
- [ ] `superseded_by` 使用列表；
- [ ] Manifest 只保留正确的建设对象；
- [ ] MOC、路线和索引已更新；
- [ ] 来源反向链接已更新；
- [ ] 项目和输出链接已抽查；
- [ ] 校验通过。
