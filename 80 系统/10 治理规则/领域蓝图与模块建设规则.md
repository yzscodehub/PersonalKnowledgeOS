# 领域蓝图与模块建设规则

## 目标

领域蓝图用于确定知识领域的长期边界、一级模块和建设入口，同时避免把规划误变成大量空目录、空 MOC 和空文章。

## 蓝图对象

每个领域只有一个正式蓝图，保存在：

```text
80 系统/50 领域蓝图/
```

蓝图属于系统设计，不属于 `30 知识` 正文。它可以规划尚未建设的模块和 MOC，但不得伪装成已完成知识。

## 必需部分

领域蓝图必须包含：

```text
领域目标
主归属边界
一级模块
核心基础
典型应用
来源与证据
实验与实践
核心 MOC
跨领域关系
首批建设建议
非目标
```

`99 跨领域知识地图`使用相同结构，但“一级模块”表示跨领域问题族。

## 模块代码

每个一级模块使用稳定代码：

```text
<DOMAIN-PREFIX>-<MODULE>
```

例如：

```text
MATH-LA
CS-ALG
GFX-PROJ
AI-LLM
SE-TEST
SYS-LINUX
ENG-UE
MEDIA-SYNC
ROBO-SLAM
```

规则：

- 模块代码用于 Manifest、迁移映射、ID 规划和自动化；
- 模块名称改善时，尽量保留代码；
- 合并或拆分模块需要 ADR 或领域蓝图修订记录；
- 模块代码不强制出现在文章文件名中。

## 逻辑模块与实体目录

一级模块默认只是逻辑规划。只有满足以下任一条件时才创建实体目录：

- 已有至少 3 篇正式文章；
- 已批准一批近期建设主题；
- 需要稳定模块 MOC；
- 已批准迁移批次需要目标路径；
- 现有内容已经因混放影响查找和维护。

禁止：

- 为蓝图中的全部模块一次性创建目录；
- 创建空 README、空 MOC 或空文章表示“结构完成”；
- 因一本书的章节结构直接创建模块；
- 因当前项目临时需要改变领域长期模块边界。

## 领域总览

领域开始正式建设时，创建一个 `map_kind: moc` 的领域总览。总览只展示：

- 领域定位；
- 已实例化模块；
- 当前核心 MOC 和学习路线；
- 已建设内容；
- 关键跨领域入口；
- 蓝图链接。

尚未实例化模块可以在“完整逻辑结构”中使用普通文本，不建立失效链接。

## 核心 MOC

蓝图中的 MOC 名称首先是规划候选。只有同时满足以下条件时才实例化：

- 有明确受众或问题边界；
- 至少存在 3 个可组织对象，或近期已批准建设；
- 不与领域总览、学习路线或索引重复；
- 有明确维护责任和退出条件。

MOC 不改变文章主归属。

## 首批建设建议

每个领域的首批建设建议只说明优先顺序，不直接创建文章。执行时必须：

1. 由项目、学习路线或迁移批次提供上下文；
2. 在 Manifest 登记稳定 ID、类型、主归属和依赖；
3. 只实例化当前真正开始建设的主题；
4. 完成一个小模块闭环后再扩大范围。

## 来源与验证

蓝图应说明该领域常用的证据类型，但具体文章仍按声明类型选择来源。蓝图不得把某一类书籍或网站声明为领域内所有问题的统一权威。

每个领域至少设计一种非文本验证方式：

- 数学与理论：推导、证明、反例、模拟；
- 工程：实现、测试、调试捕获、基准；
- 设计与内容：作品、案例、评审和用户反馈；
- 人文社科：原始资料、比较论证、数据和历史语境。

## 跨领域主题

跨领域主题按以下顺序处理：

1. 识别各子问题的抽象层；
2. 每个正式文章确定一个主归属；
3. 通用基础保留在基础领域；
4. 应用领域只解释领域特有上下文；
5. 使用跨领域 MOC 连接，不创建新的含糊顶层目录；
6. 不复制相同完整解释。

## 蓝图变更

普通调整：

- 补充应用、来源或首批建设建议；
- 调整尚未实例化模块的说明；
- 补充跨领域链接。

重大调整需要 ADR：

- 新增或删除知识领域；
- 改变领域主职责；
- 合并或拆分已广泛使用的一级模块；
- 变更稳定模块代码；
- 改变跨领域主归属规则。

## 自动校验

运行：

```bash
python scripts/check_domain_blueprints.py
```

检查：

- `01`～`13` 和 `99` 蓝图是否完整；
- 清单中的路径和领域标识是否一致；
- 11 个必需部分是否存在；
- 模块代码是否重复；
- 蓝图状态是否为 `accepted`；
- 清单与文件是否一致。
