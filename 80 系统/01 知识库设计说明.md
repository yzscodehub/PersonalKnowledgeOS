# 个人知识库总体设计方案 v3.3

> 本文是 Personal Knowledge Base 的总设计基线。目录、模板、Manifest、自动化、知识领域建设和旧库迁移，都必须服从本文确定的边界与阶段门禁。

## 0. 当前决策状态

当前进入 **总体设计评审期**。

在本方案确认前：

- 保留已经完成的数学、坐标、相机、投影和深度试点；
- 只允许修复链接、元数据、实验和明显内容错误；
- 暂停继续扩展光栅化、PBR、API、UE5、AI 等新模块；
- 不进行旧知识库的全量迁移；
- 不提前创建大批目录和空文章。

评审通过后，按 [[80 系统/02 实施路线图|实施路线图]] 分阶段建设。

# 1. 系统定位

本仓库是一套长期运行的 **个人知识操作系统**，不是资料收藏夹，也不是单一图形学百科。

它需要同时支持：

1. 捕捉临时信息；
2. 管理有结果边界的项目；
3. 维护长期责任和能力标准；
4. 建设跨领域、可复用的正式知识；
5. 保存知识来源和验证证据；
6. 记录实验、实现和工程问题；
7. 生成技术文章、视频、课程和面试材料；
8. 通过回顾、验证和项目实践持续修正知识。

完整知识生产链路：

```text
信息捕捉
  ↓
来源登记与问题识别
  ↓
理解、拆分与重组
  ↓
正式知识
  ↓
实验 / 项目 / 工程实践
  ↓
验证与修正
  ↓
文章 / 视频 / 课程 / 代码 / 决策
  ↓
反向更新知识与来源关系
```

# 2. 设计目标与非目标

## 2.1 设计目标

### 可增长

新增数学、AI、音视频、UE5、嵌入式或人文内容时，不需要重构顶层结构。

### 可复用

矩阵、概率、傅里叶分析、优化等基础知识只维护权威基础解释，被多个应用领域引用。

### 可验证

理论结论能够追溯到来源、推导、实验或生产经验。

### 可行动

知识能够进入项目、实验、面试和内容输出，而不是停留在收藏状态。

### 可维护

日常使用不依赖大量手动搬文件、填写复杂属性或维护重复索引。

### 可迁移

现有图形学知识库可以逐步迁入，同时保留旧 ID、历史链接和来源关系。

## 2.2 非目标

本系统不追求：

- 一开始覆盖所有学科；
- 把每本书逐章复刻成笔记；
- 为所有主题提前创建空 Markdown 文件；
- 让所有文章套用同一个模板；
- 用复杂插件替代清晰的信息边界；
- 为了目录完整而牺牲正文质量；
- 把所有临时想法都加工成永久笔记；
- 在缺乏验证时追求“看起来很完整”。

# 3. 总体架构

知识库由四个逻辑层组成。

```text
行动层
├── 项目
├── 责任领域
├── 输出
└── 日记与回顾

知识层
├── 数学
├── 计算机科学
├── 图形学与渲染
├── 人工智能
├── 软件工程
└── 其他知识领域

证据层
├── 书籍
├── 论文
├── 官方文档
├── 代码仓库
├── 课程与视频
├── 实验
└── 生产经验

系统层
├── 规则
├── 模板
├── MOC
├── Manifest
├── ADR
├── 自动校验
└── Git 版本历史
```

四层职责不能混合：

- 项目不复制正式知识正文；
- 来源不冒充正式知识；
- 日记不承担长期理论说明；
- 输出不作为唯一知识主版本；
- MOC 不替代具体文章；
- Manifest 不替代实际 Markdown 内容。

# 4. 顶层目录设计

```text
个人知识库/
├── 00 收件箱
├── 10 项目
├── 20 责任领域
├── 30 知识
├── 40 来源
├── 50 输出
├── 60 日记与回顾
├── 80 系统
├── 90 档案
├── _assets
├── experiments
└── scripts
```

## 4.1 目录职责

| 目录 | 职责 | 不应保存 |
|---|---|---|
| `00 收件箱` | 尚未判断归属的临时信息 | 长期知识正文 |
| `10 项目` | 有明确成果和结束条件的工作过程 | 重复的理论正文 |
| `20 责任领域` | 长期维护的责任、标准和状态 | 数学、图形学等学科正文 |
| `30 知识` | 经过理解和重组的正式知识 | 原始资料堆积 |
| `40 来源` | 书籍、论文、文档等证据入口 | 作为最终知识主版本 |
| `50 输出` | 面向他人的文章、视频、课程等成果 | 项目过程和唯一理论正文 |
| `60 日记与回顾` | 时间过程、学习记录和阶段复盘 | 稳定知识长期沉积 |
| `80 系统` | 规则、模板、Manifest、ADR 和自动化 | 普通知识正文 |
| `90 档案` | 已完成或退出日常维护的行动内容 | 仍被频繁引用的正式知识 |
| `_assets` | 图片、附件和媒体 | 可编辑正文 |
| `experiments` | 可执行最小实验代码 | 实验结论正文 |
| `scripts` | 知识库治理和校验脚本 | 学科知识实现代码 |

## 4.2 文件夹使用原则

文件夹只表达 **稳定主归属**。

不使用文件夹表达以下动态状态：

```text
进行中
等待中
已阅读
待验证
本周处理
已发布
```

这些状态使用 Properties 和动态视图管理。

# 5. 核心信息对象

## 5.1 项目 Project

定义：有明确成果、完成条件或阶段边界的工作。

示例：

- 重构个人知识库；
- 完成 PBR 渲染器；
- 制作《人类简史》第一期视频；
- 准备图形学岗位面试。

项目管理：目标、范围、里程碑、下一步、决策、问题和交付物。

项目完成后进入档案；项目产生的正式知识和输出继续保留。

## 5.2 责任领域 Area

定义：没有明确结束日期，但需要长期维持标准的责任范围。

示例：

- 职业与技术能力；
- 学习与知识管理；
- 内容创作与个人品牌；
- 健康管理；
- 财务管理。

数学和图形学不属于这里，它们属于知识学科。

统一术语：

```text
Area   = 责任领域
Domain = 知识领域
Module = 知识模块
Topic  = 知识主题
```

## 5.3 正式知识 Knowledge

定义：经过理解、重组并具有复用价值的认知内容。

正式知识需要逐步具备：

- 明确问题；
- 稳定定义；
- 原理、推导、算法或数据流；
- 边界和失败条件；
- 可靠来源；
- 与前置、应用、实验的链接；
- 与成熟度相匹配的验证。

## 5.4 来源 Source

定义：支持知识结论的原始证据或学习材料。

来源笔记记录：

- 书目信息；
- 阅读目的；
- 章节地图；
- 重要结论；
- 待验证问题；
- 已提炼知识；
- 阅读进度。

来源笔记不按章节直接充当正式知识正文。

## 5.5 输出 Output

定义：面向读者、观众、面试官或项目成员的交付成果。

项目负责生产过程，输出保存最终成果。输出可以按受众重新组织知识，但不替代正式知识主版本。

## 5.6 日记 Journal

记录某一天或阶段发生的事情、问题和下一步。日记中的稳定结论应被提炼到知识、项目或责任领域。

## 5.7 实验 Experiment

实验由两部分组成：

```text
实验文章：问题、假设、环境、步骤、结果、结论和局限
实验代码：可执行最小实现
```

实验文章进入 `30 知识/.../80 实验与实现`，代码进入 `experiments`。

## 5.8 MOC

MOC 面向人阅读，表达：

- 主题包含什么；
- 推荐学习顺序；
- 核心文章；
- 前置依赖；
- 应用和实验；
- 尚未建设内容。

## 5.9 Manifest

Manifest 面向规划和自动化，记录：

- 文章 ID；
- 标题；
- 主归属；
- 类型；
- 建设状态；
- 路线优先级；
- 前置依赖；
- 实际路径；
- 验收状态。

尚未建设的主题只存在于 Manifest 和 MOC 的普通文本中，不创建空文章链接。

# 6. 知识领域总体结构

`30 知识` 的长期规划如下：

```text
30 知识/
├── 00 知识总览
├── 01 数学
├── 02 物理与工程科学
├── 03 计算机科学
├── 04 图形学与渲染
├── 05 人工智能与数据科学
├── 06 软件工程
├── 07 系统与平台
├── 08 游戏引擎与实时应用
├── 09 音视频与多媒体
├── 10 嵌入式、机器人与智能驾驶
├── 11 设计、摄影与内容创作
├── 12 产品、商业与职业发展
├── 13 人文与社会科学
└── 99 跨领域知识地图
```

这是 **逻辑领域地图**，不是要求现在全部创建为实体目录。

## 6.1 领域实例化规则

只有满足以下任一条件时才创建实体领域或模块目录：

- 已有至少 3 篇需要长期维护的正式文章；
- 已有一个明确试点项目即将产生连续内容；
- 旧知识迁移已经完成主归属判断；
- 该模块已进入当前阶段 Manifest。

否则只在总体设计、领域 MOC 或 Manifest 中保留规划。

## 6.2 数学和应用领域边界

数学文章回答：

- 对象是什么；
- 为什么成立；
- 如何推导；
- 有哪些数学性质；
- 边界和条件是什么。

应用领域文章回答：

- 该数学结构如何解决领域问题；
- 使用什么坐标和约定；
- 如何映射到算法、GPU、API 或引擎；
- 有哪些工程失败条件；
- 如何验证和调试。

例如：

```text
数学/矩阵作为线性映射
图形学/Model、View 与 Projection
UE5/FMatrix 与 FTransform
机器人/SE(3) 位姿更新
```

它们不是重复文章，而是基础理论与不同问题上下文。

# 8. 知识文章模型

## 8.1 文章类型

| 类型 | 主要职责 |
|---|---|
| `concept` | 稳定概念解释 |
| `theory` | 定义、模型和推导 |
| `algorithm` | 输入输出、步骤、正确性和复杂度 |
| `system` | 架构、对象、数据流和生命周期 |
| `api-reference` | API 接口、参数、生命周期和平台差异 |
| `implementation` | 具体工程实现 |
| `experiment` | 可复现实验 |
| `troubleshooting` | 症状、排查、根因和修复 |
| `comparison` | 多种方案的权衡 |
| `principle` | 可复用的工程判断 |
| `map` | MOC、路线和导航 |
| `source-note` | 来源笔记 |
| `project` | 项目主页 |
| `area` | 长期责任领域 |
| `output` | 最终输出 |
| `journal` | 时间记录 |

不再维护独立的“卡片”顶层目录。原子判断放在对应知识领域，通过 `type: principle` 等属性识别。

## 8.2 文章规模原则

文章应围绕一个可以清晰命名的问题组织。

拆分信号：

- 出现两个彼此独立的核心问题；
- 一部分可以被多个领域独立引用；
- 实现、实验或故障排查已经具有独立生命周期；
- 单篇同时承担基础理论和具体平台 API 说明。

不应过度拆分：

- 每个小公式单独成文；
- 每个 API 函数单独成文但没有使用上下文；
- 文章只剩定义，没有解释、关系或应用。

# 9. 元数据设计

## 9.1 最小知识属性

```yaml
---
id: GFX-PROJ-002
type: theory
domain: graphics
maturity: draft
verification:
  - source-checked
  - derived
lifecycle: active
sources:
  - "[[Akenine-Möller 等 - Real-Time Rendering 4th]]"
created: 2026-08-04
updated: 2026-08-04
---
```

## 9.2 状态维度

### 内容成熟度

```text
seed → outline → draft → stable → evergreen
```

### 验证证据

```yaml
verification:
  - source-checked
  - derived
  - experiment-reproduced
```

验证证据为可多选列表；空列表或缺少字段表示尚无验证证据。

### 生命周期

```text
active
needs-update
deprecated
archived
```

成熟度和生命周期为单值；验证证据为可多选列表，三个维度独立维护。

## 9.3 按需属性

```text
aliases
module
contexts
prerequisites
platforms
apis
versions
version_sensitive
legacy_id
superseded_by
project
```

不要求所有笔记填写全部字段，也不在 Frontmatter 维护庞大的 `related` 列表。

## 9.4 A/B/C 优先级

A/B/C 属于某条学习路线或建设计划，不是文章的绝对属性。

例如同一篇《矩阵作为线性映射》可以在图形学和 AI 路线中都是 A，在另一个短期项目中不是当前优先项。

优先级保存在 Manifest 或学习路线中。

# 10. 链接与知识关系

成熟文章建议显式维护：

```markdown
## 知识关系

### 前置知识

### 后续知识或上层应用

### 对比与边界

### 实现与实验

### 来源
```

## 10.1 允许的主要关系

- `prerequisite`：前置；
- `derived-from`：推导来源；
- `applied-in`：应用；
- `implemented-by`：实现；
- `verified-by`：实验或生产验证；
- `compared-with`：对比；
- `superseded-by`：替代；
- `produced-by`：来源于项目；
- `used-by`：被项目或输出使用。

这些关系优先通过正文语义链接表达，而不是全部塞进属性。

## 10.2 唯一基础解释规则

一个稳定概念只维护一个完整基础解释，但允许建立领域应用文章。

判断是否重复时，不看标题是否相似，而看文章是否解决同一个问题、面向同一抽象层并重复相同定义和推导。

# 11. 来源与证据体系

## 11.1 来源权威层级

建议使用以下证据优先顺序：

1. 数学推导和可复现实验；
2. 标准、规范和官方文档；
3. 原始论文；
4. 权威教材和专业书籍；
5. 高质量技术文章和课程；
6. 代码仓库和实现行为；
7. 论坛、问答和个人经验。

低层级来源并非不可使用，但必须标明其用途和不确定性。

## 11.2 版本敏感内容

以下内容默认视为版本敏感：

- API；
- 引擎源码和工具界面；
- 平台能力；
- 驱动行为；
- 软件安装与配置；
- 法规、价格和当前产品信息。

版本敏感文章需要记录平台、版本、验证日期和官方来源。

## 11.3 验证闭环

根据文章类型选择验证方式：

- 理论：推导、反例和数值检查；
- 算法：参考实现、单元测试和复杂度验证；
- 图形算法：图像结果、Golden Image、Frame Capture；
- API：最小示例和官方规范；
- 性能：测试环境、GPU Counter 和对照实验；
- 故障：稳定复现、根因和修复后验证；
- 系统架构：数据流、生命周期、失败路径和真实项目应用。

# 12. 工作流设计

## 12.1 捕捉流程

```text
临时想法 / 链接 / 截图 / 问题
  ↓
00 收件箱
  ↓ 每周分流
项目 / 责任领域 / 来源 / 知识 / 输出 / 日记 / 删除
```

收件箱不是待办墓地。超过 30 天未处理的内容必须重新判断价值。

## 12.2 阅读到知识

```text
登记来源
  ↓
建立阅读目的和章节地图
  ↓
识别问题与稳定概念
  ↓
拆分基础理论、领域应用、实现和实验
  ↓
创建正式文章
  ↓
建立来源反向链接
  ↓
验证并更新成熟度
```

## 12.3 知识到项目

项目主页链接所需知识，但不复制正文。项目产生的新结论在稳定后提炼回知识领域。

## 12.4 知识到输出

输出可以根据读者重新组织内容，但应链接正式知识和来源。输出发布后的反馈可以反向更新知识文章。

## 12.5 回顾流程

### 每周

- 清理收件箱；
- 检查活跃项目下一步；
- 更新阅读和实验状态；
- 处理待验证和待更新文章；
- 运行校验脚本。

### 每月

- 检查 MOC 与实际文章是否同步；
- 清理重复和孤立内容；
- 评估当前建设阶段；
- 更新 Manifest 和 CHANGELOG。

### 每季度

- 审核领域结构；
- 审核来源质量；
- 审核长期未更新的版本敏感文章；
- 决定是否进入下一阶段门禁。

# 13. Obsidian 与 Git 实现

## 13.1 Obsidian 职责

- Markdown 正文；
- Wikilink 和反向链接；
- Properties；
- 模板；
- MOC 导航；
- 日记；
- Bases 或查询视图。

## 13.2 Git 职责

- 版本历史；
- 分支隔离；
- Pull Request 评审；
- 自动校验；
- 重大设计变更追踪；
- 回滚和差异审查。

## 13.3 分支策略

```text
main                       稳定可用知识库

design/*                   架构和治理变更
content/<domain>-<topic>    内容批次
migration/<scope>           迁移批次
fix/*                       链接、元数据和错误修复
```

大型内容建设不长期堆积在一个无限扩张的 PR 中。总体设计通过后，应按阶段拆分后续 PR。

## 13.4 ADR

以下变化必须创建 ADR：

- 顶层目录变化；
- 领域边界变化；
- 元数据模型变化；
- ID 策略变化；
- Manifest 结构变化；
- 核心插件或自动化依赖变化；
- 迁移策略的重大调整。

# 14. 自动化与质量门禁

当前自动校验至少包括：

- Frontmatter 是否闭合；
- 必填属性；
- 枚举值合法性；
- 重复 ID；
- 内部链接失效或歧义；
- 空壳正式文章；
- 实验脚本执行。

后续逐步增加：

- Manifest 路径和状态一致性；
- 来源反向链接完整性；
- 重复标题和重复主归属；
- 孤立核心文章；
- `deprecated` 是否包含替代关系；
- 版本敏感文章是否缺版本；
- MOC 中的规划链接是否误生成空文件；
- 文章 ID 与路径规则一致性。

质量门禁遵循渐进原则：只有规则稳定、误报可控后才升级为 CI 阻断。

# 15. 迁移策略

旧知识库迁移采用“盘点—映射—移动—修链—去重—重写”的顺序。

## 15.1 禁止做法

- 一次性全量移动；
- 移动同时大规模重写；
- 先创建所有目标目录；
- 删除旧 ID；
- 仅凭目录名判断主归属；
- 把来源摘要直接改名为正式知识。

## 15.2 迁移步骤

1. 生成旧库文件和链接清单；
2. 为每篇文章判断信息角色；
3. 判断稳定主归属和应用上下文；
4. 记录目标路径和 `legacy_id`；
5. 按小批次移动；
6. 修复内部链接和入口 MOC；
7. 识别重复基础解释；
8. 合并或拆分文章；
9. 补来源、验证和生命周期；
10. 验收后关闭该批次。

## 15.3 初步迁移映射

```text
原 M01 数学与几何分析
  → 01 数学 + 04 图形学应用

原 M02 信号、采样与颜色
  → 01 数学/信号分析 + 04 图形学/纹理与颜色

原 M03 概率与蒙特卡洛
  → 01 数学/概率与随机采样 + 04 图形学/路径追踪应用

原 C++ 与任务系统
  → 06 软件工程

原 UE5
  → 08 游戏引擎与实时应用

原神经与可微渲染
  → 04 图形学与渲染 + 05 人工智能的交叉入口
```

# 16. 建设阶段与门禁

详细任务见 [[80 系统/02 实施路线图|实施路线图]]。

- 顶层角色和边界确认；
- 知识领域规划确认；
- 元数据和状态模型确认；
- MOC、Manifest 和目录职责确认；
- 迁移原则确认；
- 阶段路线和停止条件确认。

## Gate B：试点模型验证

通过条件：

- 两本书能够转化为来源—知识—实验网络；
- 数学基础与图形学应用没有明显重复；
- MOC、Manifest 和实际文件同步；
- 自动校验稳定；
- 文章原型可用于后续主题；
- 日常维护成本可接受。

## Gate C：图形学核心建设

通过条件：

- 变换与光栅化主干完成；
- 纹理、PBR 和渲染器架构形成最小闭环；
- 至少一个 API 或渲染器项目验证知识可应用；

## Gate D：旧库迁移

通过条件：

- 小批次迁移试运行成功；
- 旧 ID 和链接兼容策略有效；
- 不出现大规模重复和孤立文章。

## Gate E：多领域扩展

只有图形学试点和迁移机制稳定后，才系统扩展 AI、音视频、UE5、嵌入式等领域。

# 17. 验收标准

## 17.1 结构验收

- 顶层目录职责无明显重叠；
- 数学与图形学平级；
- 动态状态不依赖搬文件；
- 未建设主题没有大批空文章；
- 来源、知识、项目和输出可以相互追踪。

## 17.2 正式文章验收

核心文章至少具备：

- 清晰问题和范围；
- 稳定定义；
- 必要机制、推导或数据流；
- 边界、误区或失败条件；
- 可靠来源；
- 知识关系；
- 与验证状态相匹配的证据。

## 17.3 工程文章验收

额外要求：

- 平台和版本；
- 对象生命周期；
- 线程、同步或资源约束；
- 调试方法；
- 性能影响；
- 最小示例或实验。

## 17.4 系统运行验收

- 新信息能在一分钟内判断入口；
- 每周维护不超过约 30 分钟的纯整理成本；
- 活跃项目能快速找到下一步和所需知识；
- 来源可以追踪到提炼结果；
- 实验可以重复运行；
- GitHub Actions 稳定通过；
- 新增领域不需要修改顶层结构。

# 19. 冻结决策

当前方案冻结以下原则：

1. 顶层目录按信息角色划分；
2. 数学与图形学作为平级知识领域；
3. 文件夹表达稳定归属；
4. Properties 表达动态状态；
5. MOC 表达人类可读的知识结构；
6. Manifest 表达建设计划和自动化状态；
7. 来源和正式知识分离；
8. 一个概念维护一个完整基础解释，允许领域应用文章；
9. 项目管理过程，输出保存成果；
10. 实验正文和实验代码分离；
11. 成熟度、验证证据和生命周期独立；
12. A/B/C 属于学习路线，不属于文章绝对属性；
13. 未建设文章不提前实例化；
14. 旧库采用小批次迁移并保留 `legacy_id`；
15. 新阶段必须经过门禁验收后再继续。

如需改变以上任一原则，必须更新本文并创建对应 ADR。
