# 个人知识库实施路线图

> 本路线图负责回答“先做什么、做到什么程度、什么时候停止、满足什么条件后进入下一阶段”。总体架构和边界以 [[80 系统/01 知识库设计说明|个人知识库总体设计方案]] 为准。

# 1. 实施原则

1. 先确认总体设计，再继续扩展正文；
2. 先完成小规模端到端试点，再迁移旧库；
3. 每个阶段必须有明确交付物和退出条件；
4. 不以文章数量作为唯一进度指标；
5. 不在同一个 PR 中同时进行架构调整、全量迁移和大规模内容生产；
6. 每个阶段结束时更新 Manifest、MOC、来源映射和 CHANGELOG；
7. 阶段未通过验收时，只允许修复，不扩大范围。

---

# 2. 阶段总览

```text
Phase 0  总体设计与治理基线
   ↓
Phase 1  数学—坐标—相机—投影试点
   ↓
Phase 2  实时光栅化管线试点
   ↓
Phase 3  纹理、光照与 PBR 最小闭环
   ↓
Phase 4  渲染器架构与 API 应用闭环
   ↓
Phase 5  旧图形学知识库迁移试点
   ↓
Phase 6  图形学全域迁移与完善
   ↓
Phase 7  AI、音视频、UE5 等多领域扩展
   ↓
Phase 8  稳态运维、输出与长期演进
```

# 3. Phase 0：总体设计与治理基线

## 目标

冻结知识库的系统边界、信息模型、目录职责、元数据、治理规则和实施门禁。

## 已有基础

- 顶层目录；
- 数学与图形学平级设计；
- Properties、MOC、Manifest 分工；
- 模板和 ADR；
- 自动校验脚本；
- GitHub Actions；
- 第一批试点内容。

## 本阶段交付物

- [x] 总体设计方案；
- [x] 分阶段实施路线图；
- [x] 信息归属规则；
- [x] Frontmatter 和状态模型；
- [x] MOC 与 Manifest 规范；
- [x] Obsidian 与 Git 工作流；
- [ ] 总体设计人工评审；
- [x] 顶层命名和编号语义已通过 ADR-0005、ADR-0012 固化；
- [ ] 明确旧知识库的来源位置和迁移范围；
- [ ] 将设计 PR 调整为可评审状态。

## 退出条件

- 总体设计中的 15 条冻结原则得到确认；
- 顶层目录和领域边界不再反复变化；
- 后续阶段的范围、顺序和停止条件明确；
- 确认当前试点内容可以作为文章原型；
- 决定当前 Draft PR 是合并为架构基线，还是继续承载 Phase 1 收尾。

## 当前状态

`review`

在通过前暂停新增光栅化、PBR 和其他领域正文。

# 4. Phase 1：数学—坐标—相机—投影试点

## 目标

验证一本基础教材和一本综合实时渲染教材能否被转化为：

```text
来源 → 数学基础 → 图形学应用 → 可执行实验 → MOC / Manifest
```

## 已完成内容

### 数学

- 点与向量；
- 向量空间；
- 基与坐标；
- 矩阵作为线性映射；
- 仿射空间与仿射组合；
- 标架与坐标系；
- 齐次坐标。

### 图形学

- 图形学坐标空间总览；
- Object 到 World；
- World 到 View；
- 正交投影；
- 透视投影；
- Clip Space、透视除法与 NDC；
- 深度缓冲、精度与 Reversed-Z。

### 实验

- 矩阵乘法和坐标约定；
- 正交与透视投影端点；
- Float32 深度精度和 Reversed-Z。

## 尚需完成

- [ ] 统一复核所有矩阵约定和符号；
- [ ] 为来源笔记补充精确章节或页码；
- [ ] 检查数学文章与图形应用文章是否存在重复；
- [ ] 审核实验结果与文章验证状态是否匹配；
- [ ] 检查 MOC 和 Manifest 是否完全同步；
- [ ] 对文章模板做一次回顾并删除不必要章节；
- [ ] 记录本阶段复盘。

## 退出条件

- 来源、知识和实验之间可以双向追踪；
- 所有试点文章通过结构和链接校验；
- 文章原型的维护成本可接受；
- 不依赖反复移动文件管理状态；
- 至少一条学习路线可以完整走通；
- 形成 Phase 1 复盘和 Phase 2 范围确认。

# 5. Phase 2：实时光栅化管线试点

## 目标

建立从 CPU 提交到像素输出的主干，并验证算法文章、系统文章和最小软件实验的组织方式。

## 范围

### 核心文章

1. CPU 到 GPU 帧流程；
2. 顶点输入与顶点处理；
3. 图元装配与裁剪；
4. 光栅化与覆盖规则；
5. 重心坐标；
6. 透视正确插值；
7. Pixel Shader Quad 与导数；
8. 深度、模板和 Early-Z；
9. 混合与输出合并；
10. Present 与 Frame Pacing 总览。

### 实验

- 三角形边函数和覆盖测试；
- Top-Left Rule；
- 重心坐标；
- 透视正确与错误插值对比；
- 深度测试和简单混合；
- 最小软件光栅器图像输出。

## 非目标

- 不深入 DX12/Vulkan 命令提交细节；
- 不进入完整 Shader 编译系统；
- 不建设完整 GPU 架构模块；
- 不扩展到材质、纹理和 PBR。

## 退出条件

- 一条三角形从顶点到像素的完整知识链可运行；
- 软件实验能够输出可检查结果；
- 光栅化文章与 API 无关的原理边界清晰；
- 与后续纹理、深度、Shader 和 API 模块的接口明确；
- CI 能自动验证关键算法不变量。

---

# 6. Phase 3：纹理、光照与 PBR 最小闭环

## 目标

完成从几何覆盖到材质着色和显示输出的最小渲染闭环。

## 范围

### 纹理与采样

- UV 和寻址；
- Bilinear、Trilinear 和 Mipmap；
- LOD 与导数；
- sRGB 与线性空间；
- Normal Map 与 TBN；
- 纹理压缩概览。

### 光照与 PBR

- 辐射度学最小基础；
- BRDF；
- 微表面模型；
- Fresnel、NDF 和 Geometry Term；
- Cook-Torrance；
- Metallic-Roughness；
- IBL 最小链路；
- Tone Mapping。

### 实验

- Mipmap 与混叠；
- sRGB 错误对比；
- Normal Map 空间验证；
- BRDF 项可视化；
- 能量守恒检查；
- CPU 或 Shader 最小 PBR 示例。

## 退出条件

- 从纹理采样到最终颜色输出形成闭环；
- 数学、信号和图形学边界清晰；
- PBR 文章可被实际渲染器项目引用；
- 至少一个图像对比或参考测试可重复运行。

---

# 7. Phase 4：渲染器架构与 API 应用闭环

## 目标

证明知识库不仅能解释理论，也能指导真实渲染器和跨 API 工程设计。

## 范围

### 通用架构

- Renderer 分层；
- Scene 与 Render Scene；
- RHI；
- Resource 与 View；
- Descriptor；
- PSO；
- Shader 系统；
- RenderGraph；
- GPU Scene；
- 多线程和资源生命周期。

### API 映射

优先按统一概念横向对比：

```text
Buffer
Texture
Resource View
Pipeline State
Descriptor / Binding
Command Submission
Synchronization
Render Pass
Shader Compilation
```

再映射到：

```text
DX11 / DX12 / Vulkan / Metal / OpenGL
```

## 项目验证

至少选择一个最小渲染器或既有工程：

- 实现坐标、光栅化、纹理和 PBR；
- 记录 API 对象和生命周期；
- 记录性能和调试证据；
- 把项目经验提炼回正式知识。

## 退出条件

- 理论文章、系统文章、API 文章和项目记录职责清晰；
- 至少一个真实实现验证主干知识；
- 跨 API 笔记不再按平台孤立重复；
- 具备迁移旧 API 和引擎文章的目标结构。

# 8. Phase 5：旧图形学知识库迁移试点

## 目标

使用小批次验证迁移方法，不直接全量搬迁。

## 试点范围建议

从旧库选择一个闭环模块，例如：

- 数学与变换；
- 纹理与采样；
- PBR；
- RHI 与资源系统。

建议首批控制在 20～50 篇。

## 工作项

- [ ] 导出旧文件清单；
- [ ] 导出旧链接和 ID；
- [ ] 建立逐篇迁移映射；
- [ ] 区分正式知识、来源摘要、项目记录和故障笔记；
- [ ] 记录 `legacy_id`；
- [ ] 小批次移动；
- [ ] 自动修链和人工抽查；
- [ ] 合并重复基础解释；
- [ ] 补来源和验证状态；
- [ ] 完成迁移复盘。

## 退出条件

- 旧 ID 和历史链接可追踪；
- 没有大规模断链；
- 重复内容减少而不是增加；
- 迁移过程可以复用到下一批；
- 迁移成本和速度可估算。

---

# 9. Phase 6：图形学全域迁移与完善

## 目标

把现有图形学知识资产逐步迁入新系统，同时补齐缺失的主干和验证。

## 建议批次顺序

1. 数学、概率、信号基础；
2. 几何和空间变换；
3. 光栅化、纹理和颜色；
4. 光照、材质、阴影和后处理；
5. GPU、API 和渲染器架构；
6. 性能、调试和工程案例；
7. 光线追踪、离线渲染和前沿技术；
8. UE5 和内容管线迁往对应独立领域。

## 退出条件

- 旧图形学库不再存在未登记的孤立核心内容；
- 每个主模块有 MOC 和来源入口；
- 核心文章达到 `stable` 或有明确待办；
- API 和版本敏感内容具有版本标记；
- 旧库可以只读归档。

---

# 10. Phase 7：多领域扩展

## 顺序建议

```text
软件工程
  ↓
游戏引擎与实时应用
  ↓
音视频与多媒体
  ↓
人工智能与数据科学
  ↓
系统与平台
  ↓
嵌入式、机器人与智能驾驶
  ↓
设计、摄影与内容创作
```

顺序可以根据当前项目调整，但每个新领域都要先完成：

1. 领域边界；
2. 领域总览；
3. 学习路线；
4. 一个小规模试点；
5. 来源入口；
6. 验收后再扩展。

---

# 11. Phase 8：稳态运维与输出

## 目标

让知识库从一次性建设项目转为长期低成本运行系统。

## 稳态机制

- 每周收件箱和项目检查；
- 每月 MOC、Manifest 和来源检查；
- 每季度领域和版本敏感内容审查；
- 文章、视频和面试材料从正式知识生成；
- 项目实践持续反哺知识；
- 自动校验和实验长期运行；
- 重大架构变化通过 ADR 和独立 PR。

## 衡量指标

不只统计文章数，还关注：

- 活跃项目是否能找到所需知识；
- 来源是否转化为正式知识；
- 文章是否有验证；
- 知识是否产生输出；
- 重复和断链是否受控；
- 日常维护时间是否可接受；
- 版本敏感内容是否及时更新。

# 12. 当前下一步

在总体设计评审完成前，只执行：

1. 审核 [[80 系统/01 知识库设计说明|总体设计方案]]；
2. 审核本路线图的阶段顺序和门禁；
3. 复核当前 Phase 1 试点是否过度建设或缺少关键内容；
4. 决定 Draft PR #1 的合并边界；
5. 暂停开始 Phase 2 正文生产。

评审通过后，再创建独立的 Phase 2 内容分支和 PR。
